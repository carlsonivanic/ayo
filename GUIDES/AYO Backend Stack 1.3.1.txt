====================================================================
1. SCOPE & GOALS
====================================================================

1.1 Purpose
Backend for AYO, the sales & coordination app for SellMore POS.
Handles L1/L2 agents, payment links (QRIS/card), subscription codes,
lifetime seats with path-lock, commission engine, payouts, admin
operations, reports, authentication/authorization, and the
SellMore-embedded SDK API.

1.2 Business Targets — [ASSUMPTION — confirm with owner]
- 1,000,000 SellMore merchants in first 2 years. (Not in locked spec.)
- Distribution ~80% subscribers / 20% lifetime. (Not in locked spec.)

1.3 Derived Load Profile (depends on §1.2 assumptions — see DI-3)
- ~41,700 new merchants/month ≈ 1,400/day; renewals worst-case
~13,000/day (peaks 20-50 req/s).
- Highest-frequency endpoints: SDK lookups by sellMoreStoreId (cacheable).
- Data volume ≈ 5-20 GB over 2 years.
- Conclusion: data-volume + business-rule problem, not throughput.


====================================================================
2. TECHNOLOGY STACK DECISION
====================================================================

2.1 Chosen Stack: Convex.dev
- Reactive TypeScript backend-as-a-service.
- Database: Convex document DB (ACID transactions per mutation).
- Functions: query (reactive), mutation, action, internalMutation.
- HTTP: httpAction + httpRouter for payment webhooks.
- Cron: built-in crons (daily/weekly/monthly/interval).
- Auth: @convex-dev/auth (email OTP) + Resend for OTP email delivery.

2.2 Why Convex
- Real-time dashboards: PENDING -> CONFIRMED flips live, zero polling.
- TypeScript end-to-end; shared types with the PWA.
- Built-in scheduler fits monthly/weekly job profile.
- Transactional mutations suit the append-only ledger.
- Generous free tier for MVP.

2.3 Options evaluated and set aside
| Option | Verdict |
| NestJS + PostgreSQL | Strong fallback if Convex limits are hit |
| Supabase (Postgres) | Best BaaS free tier; awkward for heavy batch |
| Laravel + Filament | Best if admin UI speed / ID talent dominates |
| Go + PostgreSQL | Cheapest runtime; slower dev velocity for rules |
| Next.js + Neon | Weakest for background jobs |
| Cloudflare D1 | Great SDK latency; worker CPU limits hurt batch |
| MongoDB | Poor fit for relational overrides & SQL-style reports |

2.4 Known Convex constraints (mitigations)
- No SQL GROUP BY -> maintain monthly summary docs; reports read summaries.
- Heavy exports -> CSV in actions; PDF via PWA print stylesheet.
- Long month-end jobs -> fan out one scheduled mutation per L1.
- Free tier pauses on inactivity -> paid plan before real money.


====================================================================
3. ARCHITECTURE PRINCIPLES
====================================================================

P1 (REVISED). Append-only ledger. No SELF-SERVICE refunds/cancellations.
Admin may process manual refund exceptions with reason + audit
(§3.6/§19.1/Edge 31; chargeback Edge 17 -> admin adjustment). Earnings
are INSERTed; provisional PENDING records are resolved, never deleted.

P2. Provisional PENDING earnings. Created at payment to the SELLER
(tentative NEW_SALES at Y1). Resolved at redemption:
- First-time: patch to CONFIRMED NEW_SALES (amount finalized).
- Renewal: seller patched to CONFIRMED RENEWAL_INCENTIVE (2%); owner's
RECURRING is a fresh insert. Never deleted.

P3. Acquisitions are first-class events (separate table): expired-unused
code keeps the NEW_SALES earning but must NOT count as acquisition (§6.2).
Warmth/Jaminan/Target count acquisitions.

P4. Short-lived codes (max 7 days). USED/EXPIRED codes are dead artifacts;
only a lightweight reissue index retained.

P5 (REVISED). 90-day live retention is [EXTENSION / backend decision],
not in locked spec. ARCHIVAL GUARANTEE: archival NEVER removes data
required by locked features. Retained long-term (exempt from archival):
monthlyL1Summaries, monthlyL2Summaries, merchantEarningHistory,
acquisitions, payoutLines, and all lifetimeSeats (esp. unactivated).
Verification tests VT-1..VT-4 (§6.2).

P6. Idempotent webhooks (link-status guard + gateway idempotency key);
Convex serializes per-document mutations.

P7. Earning month follows PAYMENT date; acquisition month follows
REDEMPTION date (§6.1).

P8. Payouts pay ONLY CONFIRMED earnings (§11.8).

P9. Never trust client-supplied identity; derive from authenticated session.

P10. Separate auth domains: PWA session auth vs SDK/webhook service auth.

6.3 Mobile normalization (users.mobile) — applied on EVERY write
Write paths: registerPublic, registerViaInvite, adminCreateUser, profile/
self-update, admin user edit. Store ONLY the normalized value.
Step 1 Clean: strip all whitespace and dashes (accept and ignore).
"0811 1234 5678" -> "081112345678"; "0811-1234-5678" -> "081112345678".
Step 2 Auto-prefix to E.164:
starts with "0"        -> replace leading 0 with +62 (0811xxx->+62811xxx)
starts with "+62"      -> keep as-is
starts with "62" (no+) -> prepend "+"  [MD-1: confirm]
starts with other "+"  -> keep as-is (international) [MD-2: default accept]
otherwise              -> reject as invalid
Step 3 Validate (MD-2-aware; Empty/omitted allowed — optional field):
- Starts with "+62": must be +62 followed by 8-12 digits; else reject.
- International (other "+"):
    * MD-2 = accept (default): accept if plausible E.164 (leading +,
      7-15 digits total); else reject.
    * MD-2 = reject (ID-only): reject any non-+62 value.
- CONSISTENCY NOTE: Step 2 preserves international values; Step 3 must
  NOT unconditionally reject them. Behavior follows MD-2. Until MD-2 is
  decided, default = accept (matches MD-2 label).
Uniqueness: Convex has no native unique index; enforce in write mutation via
by_mobile lookup. Enforce uniqueness on non-empty mobile from day one. On
profile edit, exclude the user's own current value. Mobile is informational
only in MVP (no OTP/login); auth stays email OTP (§3.1).

7. CORE FLOWS
====================================================================

7.1 Subscription sell flow (unchanged)
createPaymentLink (single-use, 24h) -> WhatsApp -> gateway webhook ->
processPayment (idempotent): guard link.status != SHARED -> dedupe;
FAILED -> FAILED; PAID -> generate code (UNUSED,7d) + insert PENDING earning
to seller (tentative NEW_SALES, price x y1Percent) + notify L1 -> L1 sends code.

7.2 Lifetime sell flow (REVISED — C1)
createLifetimeDeepLink -> buyer taps -> SellMore identifies ->
pathLockCheck(sellMoreStoreId) BEFORE payment: look up merchant; NO row =
PROSPECT -> allow; row SUBSCRIBED/CHURNED/LIFETIME -> block + admin notify.
pathLockCheck creates NO merchant row. Buyer pays (identity carried as
buyerSellMoreStoreId) -> onLifetimePaid: CONFIRMED NEW_SALES to seller =
price x oneTimePercent; seat pool created (Single=1/Duo=2) tagged with
buyerSellMoreStoreId. Single: seat AUTO-ACTIVATES for buyer at payment ->
merchant row created as LIFETIME at this activation. Duo: seats POOLED
until activation.

7.3 Code redemption (redeemSubscriptionCode)
Identity (sellMoreStoreId) known only here. Lookup code; reject USED/EXPIRED.
- FIRST-TIME (new merchant): owner=seller (permanent); merchant row created
SUBSCRIBED; seller PENDING -> CONFIRMED NEW_SALES (price x y1Percent);
acquisition recorded (period=redemption month); code USED, FIRST_ACTIVATION.
- RENEWAL (existing): ownerRecurring = price x yRate(merchant tenure at
payment date); seller PENDING -> CONFIRMED RENEWAL_INCENTIVE (price x 2%);
owner RECURRING inserted (CONFIRMED; frozen=true if owner SUSPENDED);
ownerless owner -> no owner line (company retains Y); seller still 2%;
subscription extended from USED date; code USED, RENEWAL; NO acquisition;
ownership unchanged.
- After 36-month window: ownerRecurring = 0.

7.4 Lifetime seat activation (activateLifetimeSeat)
Self (seatId) or gift (seatToken). Expired gift link -> regenerate.
L3 re-verify PROSPECT (no row). PROSPECT -> seat ACTIVATED, merchant row
created LIFETIME (terminal), owner=sellerL1Id, acquisition recorded.
Non-PROSPECT -> seat returns to POOLED (re-giftable, no refund); notify.

7.5 Seat gift links (regenerateSeatLink)
Buyer-only; sets GIFT_LINK_ACTIVE + token; 30-day expiry; value remains;
regenerationCount increments.

7.6 Self-renewal (reportSelfRenewal)
Identity known; owner Y-rate RECURRING CONFIRMED immediately; no 2%; no
acquisition; frozen=true if owner SUSPENDED; period extended. Honors
plan.renewalPrice when present (NEW_SALES_ONLY lock).


====================================================================
8. FINANCIAL ENGINE (MONTH-END)
====================================================================

8.1 Schedule: month-end close runs on the 8th for the previous month (by
then every prior-month code is USED or EXPIRED = CONFIRMED).

8.2 Execution: closePreviousMonth fans out one idempotent processL1Month
per L1 (skips if summary exists; stays within transaction limits).

8.3 processL1Month logic
- tenureMonth = calendar months since firstPaymentAt (payment month = M1).
- activationCount = acquisitions in period.
- gross = CONFIRMED (NEW_SALES + RECURRING + RENEWAL_INCENTIVE); PENDING excluded.
- Jaminan: if tenureMonth <= 3 AND activations >= 8 AND gross < 3,000,000
-> jaminan = 3,000,000 - gross.
- Warmth (only after month 3; §8.4 months 1-3 = guarantee, no warmth):
    * activations >= 5 -> WARM; held 0; release ALL heldBalance; AND reset
      consecutiveSub5Months = 0.
    * activations < 5  -> consecutiveSub5Months + 1; >=3 -> COLD (50% held)
      else COOL (20% held).
    * consecutiveSub5Months increments ONLY in warmth-eligible months
      (tenureMonth >= 4); it does NOT accrue during months 1-3.
- HeldRecord written; l1State.heldBalance updated.
- L2 fee: if assignedL2Id AND tenureMonth >= 7: effective fee by decay;
  l2Base = gross; if schemeSettings.l2.includeJaminan THEN
  l2Base = gross + jaminan (same-period jaminan). l2Fee = l2Base x
  effective%; insert l2EarningLine (l1Gross = l2Base); accumulate
  monthlyL2Summaries. Default includeJaminan=false -> base = gross only
  (excl Jaminan; §16.4/§16.7).
- Insert monthlyL1Summary (settled=false).

HELD RELEASE TIMING — DECISION ITEM DI-1 (B3). Locked §9.1: "Hit 5+ new
customers in any month -> ALL held released in full." L1 Scheme §5: "As soon
as you hit 5+ new customers in any month, ALL previously held money is
released to you in full." Options: (a) immediate release when the month's 5th
acquisition is recorded (in redeemSubscriptionCode/activateLifetimeSeat), or
(b) release at month-end close (current implementation). PRODUCT DECISION
REQUIRED. Default implemented: (b), pending DI-1. Held ACCRUAL (Cool/Cold)
remains month-end; only RELEASE timing is in question.

8.4 Frozen owner commissions
Owner SUSPENDED at renewal/self-renewal -> owner RECURRING frozen=true.
Liability report sums frozen CONFIRMED earnings. Admin resolves (§10.4).

8.5 Daily maintenance crons
expireUnusedCodes; expireSeatLinks; markChurnedMerchants; archiveOldLive
(respects §6.2 guarantees); notifyExpiringCustomers (<=7d); notifyWindowEnded.


====================================================================
9. PAYOUT ENGINE
====================================================================

9.1 Schedules: L1 weekly default (Mon-Sun -> Wed), monthly override
(1st-last -> 5th); L2 monthly (5th).

9.2 Payable formula (§11.4): Payable = Gross + Jaminan - Held + ReleasedHeld
+/- Adjustment. Gross = CONFIRMED (new sales + recurring + renewal incentive).

9.3 Weekly/monthly reconciliation — DECISION ITEM DI-2 (B4). Pay-as-you-go
with monthly true-up kept: weekly pays the week's CONFIRMED gross; monthly
accruals (held/jaminan/release) carry settled and are consumed once by the
first payout after month-close. NOTE §11.4 implies held is deducted in the
period earned; weekly true-up defers this. Consequence: month M's held is
clawed back after close, so the L1 is temporarily overpaid during month M.
Alternative: force monthly payout for held-affected L1s. PRODUCT DECISION
REQUIRED (DI-2).

9.4 Guards: ACTIVE only (SUSPENDED -> admin resolution; Edge 5/8); payout
profile required (§11.7); idempotent per (user, period); zero-activity -> no
line. Weekly keys use day granularity; cross-month weeks query both months.

9.5 Mark paid (§23.3): requireAdmin; SCHEDULED -> PAID; notify; audit.

9.6 L2 payout: Σ l2EarningLines.l2Fee for period +/- adjustments; profile required.

10. ADMIN REPORTS, OPERATIONS & MEMBER DATA QUERIES
====================================================================

10.1 Reports (§24, all requireAdmin, read summaries)
- P/L (§24.2): Revenue - L1(new+recurring) - renewal incentive - L2 - Jaminan
= Net profit. Revenue = PAID payment links in period.
- Liability (§24.3): L1 unpaid (SCHEDULED payouts) + L1 held (heldBalance) +

17. BUSINESS RULES QUICK REFERENCE
====================================================================

17.1 Pricing & commission: Monthly 70.000 | Yearly 600.000 | Lifetime Single
1.500.000 (33.33% = 500.000) | Lifetime Duo 2.000.000 (35% = 700.000).
Y1 50% (0-12m) | Y2 40% (12-24) | Y3 30% (24-36) | Y4+ 0% (36+). Window = 36
months from merchant FIRST payment; rate by PAYMENT date. Renewal incentive
2% to seller; never first-time/lifetime/self-renewal.
17.2 Jaminan (first 3 months): activations >= 8 AND gross < 3.000.000 ->
top-up to 3.000.000.
17.3 Warmth (after month 3; first-time activations): Warm 5+ -> 100%/0 held |
Cool <5 -> 80%/20 held | Cold 3x<5 -> 50%/50 held. Hit 5+ -> ALL held released.
Held NEVER forfeited.
17.4 L1 targets: M1-3:10 | M4-6:12 | M7-9:15 | M10-11:18 | M12+:20.
17.5 L2: 10% base; starts M7; M7-18 10% | M19-30 6.6% | M31-42 3.3% | M43+ 0.
Base = L1 gross (incl held + renewal incentive), excl Jaminan (or incl Jaminan
if includeJaminan enabled).
17.6 Lifecycles: link 24h | code 7d | seat link 30d (value remains). Single
lifetime auto-activates at payment. Duo = pool, giftable. Blocked seat returns
to pool; no refund. Ownerless stays ownerless.
17.7 Payouts: L1 weekly Mon-Sun -> Wed (default); monthly 1st-last -> 5th.
L2 -> 5th. Payable = Gross + Jaminan - Held + ReleasedHeld +/- Adjustment.
17.8 Roles & auth: Roles L1/L2/ADMIN. Statuses PENDING/ACTIVE/SUSPENDED.
Login email OTP only. Registration admin create / public / L2 invite. Admin
gates all reports & admin mutations; identity from session.
17.9 PROSPECT = absence of a merchant row (§39.2); stored statuses only
SUBSCRIBED|CHURNED|LIFETIME.
